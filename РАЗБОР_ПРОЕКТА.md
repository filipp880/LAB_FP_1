# Как устроен проект резервного хранилища

Этот файл объясняет проект целиком. В исходниках оставлены короткие комментарии
к важным функциям и неочевидным решениям. Пустые строки отделяют части программы.

Удобный порядок изучения: сначала этот разбор, затем `Main.scala`,
`Command.scala`, `AppError.scala`, `Models.scala`, `Sources.scala`,
`Menu.scala`, `Scanner.scala`, `Container.scala` и остальные вспомогательные файлы.

## 1. Что делает программа

У пользователя есть исходные файлы, например `Desktop/FP-test/a.txt`.
Программа сохраняет их содержимое в один файл, например `Desktop/demo.store`.
Позже исходный файл можно изменить или удалить, а сохранённую копию — восстановить.

Различай три места:

| Место | Пример | Назначение |
|---|---|---|
| Источник | `FP-test/a.txt` | Оригинал, который пользователь меняет |
| Хранилище | `demo.store` | Файл с сохранёнными данными и историей |
| Каталог восстановления | `FP-restored` | Папка, куда программа записывает выбранную копию |

Команда проверки изменений только читает источники и показывает отчёт.
Для сохранения нужна отдельная операция резервирования и, по настройке,
подтверждение. Для восстановления выбираются версия и папка назначения.

## 2. Какие файлы за что отвечают

```text
ЛР1/
  src/backup/
    Main.scala        — запуск
    Menu.scala        — вопросы, ответы, вывод и цикл меню
    Command.scala     — допустимые команды и их разбор
    AppError.scala    — допустимые ошибки и граница исключений Java
    Config.scala      — чтение и проверка настроек
    Models.scala      — описания файлов, снимков и отчётов
    Sources.scala     — описание и проверка источника
    Scanner.scala     — обход источников и поиск изменений
    Container.scala   — чтение/запись контейнера, версии, восстановление
    Crypto.scala      — хеши, генерация ключа и стандартное шифрование
    Glob.scala        — правила исключения файлов
    Logger.scala      — дописывание журнала
  tests/BackupChecks.scala — автоматические проверки
  project.scala           — настройки запуска через Scala CLI
  build.sbt               — настройки сборки через sbt/IDEA
  project/build.properties — версия sbt
  run.cmd                 — запуск на Windows
```

Во время работы появляются `backup.json`, `backup.log` и, при сохранении ключей,
папка `keys`. Это рабочие данные. `.idea`, `.scala-build`, `target` и `.bsp`
создают IDEA и инструменты сборки; они не содержат основной логики лабораторной.

В проекте две группы кода. Интерфейс в `Menu` разговаривает с пользователем.
Остальные основные функции получают аргументы и возвращают результаты.
Например, `Container.backup` не спрашивает «сохранять?»: это уже решил интерфейс.

## 3. Как начинается выполнение

В `Main.scala` функция с `@main` называется `backupApp`.
Аннотация позволяет запускать её как точку входа приложения.

Последовательность такая:

1. Определить путь к `backup.json` в текущей рабочей папке.
2. Если файла нет, сохранить стандартные настройки.
3. Загрузить настройки и проверить их.
4. При ошибке показать её сообщение.
5. При успехе создать `Menu` и вызвать `run()`.

Внутри `run()` программа записывает запуск в журнал, показывает меню,
читает ответ, превращает его в команду и выполняет. Затем повторяет цикл.
Ноль, `exit` или окончание входного потока завершают работу.

Пути в конфигурации, например `keys` или `backup.log`, относительные.
Они отсчитываются от рабочей папки запущенной программы, а не от расположения
файла `Main.scala`. Поэтому удобно запускать приложение из папки `ЛР1`.

| Запись | Простое объяснение |
|---|---|
| `package backup` | Все эти определения принадлежат одной группе с именем backup |
| `import ...` | Разрешает обращаться к библиотечным классам короткими именами |

| `${...}` | Подстановка результата выражения в строку |

| `_.number` | Сокращение функции `x => x.number` |

| `Set[A]` | Набор без повторов, удобный для проверки наличия элемента |
| `Map[K, V]` | Таблица: по ключу типа K можно получить значение типа V |

В Scala 3 отступы определяют вложенность. Двоеточие после `object` или `class`
начинает их тело. Фигурные скобки здесь часто ограничивают функцию,
переданную в `map`, `foreach` или другой метод.

`val` фиксирует ссылку, но не делает автоматически неизменяемым любой объект.
Например, Java-поток или `ujson.Obj` может менять внутреннее состояние.
Основные модели программы — неизменяемые записи, обновляемые через `copy`.

## 5. Главная идея ЛР1: команды и ошибки как значения

### ADT

ADT — тип, состоящий из заранее перечисленных вариантов.
В этой программе для него используется `enum`.

Например, `Command` бывает `Create`, `Open`, `Scan`, `Backup(comment)` и так далее.
У `Backup` есть данные — необязательный комментарий.
У `Sources` есть вложенное действие `SourceAction`: добавить, изменить,
удалить или включить источник.

`Command.parse` один раз разбирает строку вроде `6` или `backup перед изменениями`.
Дальше `Menu.execute` получает готовый вариант команды.
Ему не требуется снова искать в строке слова и аргументы.

`AppError` устроен так же. `WrongKey`, `FileMissing(path)` и `FileChanged(path)`
описывают разные причины неудачи. У каждого варианта есть понятное `message`.
Получение этого сообщения ничего не печатает; вывод выполняет `Menu` или `Main`.

### Option

`Option[A]` означает: значение типа A может присутствовать или отсутствовать.

```scala
Some(5)   // Значение есть: число 5.
None      // Значения нет.
```

Примеры в проекте:

- `opened: Option[StorageMeta]` — хранилище ещё может быть не открыто.
- `key: Option[String]` — обычному контейнеру ключ не нужен.
- `comment: Option[String]` — пользователь может не писать комментарий.
- `lastVersion` — у нового хранилища ещё нет сохранённых версий.
- `FileRef.hash` — `None` отмечает отсутствие файла в данном состоянии.

`read()` различает `None` при окончании ввода и `Some("")` при Enter.
Enter — реальный ответ, который некоторые вопросы понимают как выбор по умолчанию.

При выборе ключа встречается `Option[Option[String]]`.
Здесь два разных вопроса: продолжился ли диалог и нужен ли вообще ключ.
`None` снаружи означает отмену, `Some(None)` — успешный выбор контейнера
без шифрования, `Some(Some(key))` — успешный выбор зашифрованного контейнера.

### Either

`Either[AppError, A]` означает: операция вернула ошибку или результат типа A.

```scala
Right(result)                  // Успешный результат.
Left(AppError.WrongKey)         // Известная причина неудачи.
```

Например, `Container.open` возвращает либо `Right(StorageMeta)`,
либо `Left` с причиной: файл отсутствует, ZIP повреждён или ключ неверен.
Ошибка является обычным возвращаемым значением. Для неё не нужен `throw`.

Функция `Boundary.attempt` нужна для Java API: ОС и библиотеки могут бросать
исключения при чтении, записи или проверке доступа. На этой границе исключение
переводится в `Left`. Известные ошибки самой задачи создаются непосредственно
через варианты `AppError`.

### map, flatMap и for

`map` преобразует успешное значение, сохраняя его контейнер.

```scala
Some(5).map(_ * 2)                 // Some(10).
Right(5).map(_ * 2)                // Right(10).
List(1, 2, 3).map(_ * 2)           // List(2, 4, 6).
```

Для `Either` преобразуется `Right`; обычный `map` не выполняется для `Left`.
Для `Option` он не выполняется для `None`.

`flatMap` нужен, когда следующий шаг сам возвращает контейнер.
Например, чтение пути уже возвращает `Either`, а проверка прочитанного JSON
тоже возвращает `Either`. `flatMap` соединяет их без `Either` внутри `Either`.

```scala
for
  config <- Config.load(path)
  _ <- Config.save(copyPath, config)
yield config
```

Это учебный пример: загрузить конфигурацию, сохранить её копию и вернуть
загруженное значение. Если первый шаг вернёт `Left`, второй не выполнится.
Подчёркивание означает, что успешный результат `Unit` сохранять не требуется.

`for` — удобная запись через операции контейнеров. Он не всегда означает
обычный цикл: для `Either` и `Option` это последовательность успешных шагов,
а для списков — перебор. `for ... do` выполняет побочные действия,
`for ... yield` строит возвращаемое значение.

Другие методы, которые часто встречаются:

| Метод | Смысл в этом проекте |
|---|---|
| `filter` | Оставить подходящие элементы, например разрешённые перезаписи |
| `filterNot` | Убрать подходящие элементы, например удалённые источники |
| `foreach` | Выполнить действие для элементов: напечатать строки или записать файлы |
| `collect` | Выбрать подходящие варианты и сразу получить из них нужные данные |
| `foldLeft` | Пройти коллекцию, перенося накопленный результат на следующий шаг |
| `fold` | Выбрать, что делать при отсутствии/ошибке и при наличии/успехе |
| `toRight(error)` | Превратить Some в Right, а None — в указанную ошибку Left |
| `toOption` | Взять успешное значение; в этом проекте ошибки при этом собираются отдельно |
| `getOrElse(default)` | Получить значение или осмысленный стандартный вариант |
| `lift(index)` | Безопасно получить элемент по индексу как Option |
| `left.map(...)` | Изменить только ошибку Either, оставив успешный результат как есть |

## 6. Какие данные описаны в Models и Sources

### Source

`Source` — один выбранный файл или каталог.

| Поле | Смысл |
|---|---|
| `path` | Исходный путь |
| `includeSubdirs` | Нужно ли обходить вложенные папки |
| `exclusions` | Дополнительные шаблоны исключений |
| `enabled` | Нужно ли сейчас копировать источник |
| `lastBackup` | Дата последней успешной копии либо None |
| `removed` | Источник удалён из видимого списка, но его номер сохранён для истории |

Номера источников важно сохранять. Первый источник получает внутренний префикс
`s0`, второй — `s1`. Если физически убрать первый элемент списка и сдвинуть
остальные, старые пути `s1/...` начнут обозначать другую запись.
Поэтому удаление ставит флаг `removed`, а не перенумеровывает историю.

`Source.validate` проверяет вводимый путь и исключения.
`available` определяет текущую доступность, `status` переводит её в текст.
Недоступный источник остаётся известен хранилищу и может снова появиться позже.

### FileRef и VersionInfo

`FileRef` хранит ссылку на содержимое одного файла: `hash` и `size`.
Хеш — вычисленный по байтам отпечаток содержимого.
По нему программа находит сохранённый блок и проверяет целостность.
`None` вместо хеша означает, что в этом состоянии файл отмечен удалённым.

`VersionInfo` — один снимок состояния:

| Поле | Смысл |
|---|---|
| `number` | Номер версии |
| `timestamp` | Дата и время создания |
| `comment` | Необязательная заметка пользователя |
| `result` | `success`, `partial` либо отметка об очистке старых данных |
| `added`, `modified`, `deleted` | Списки изменений именно этой операции |
| `renamed` | Пары старого и нового пути для совпавшего содержимого |
| `bytes` | Суммарный размер успешно прочитанных новых/изменённых файлов |
| `snapshot` | Таблица всего состояния: внутренний путь → FileRef |

Списки изменений и `snapshot` решают разные задачи.
Список `added` отвечает «что добавилось сейчас?», а `snapshot` —
«какие файлы должны присутствовать в этой версии?».

### StorageMeta

Это описание всего хранилища: название, реальный путь, шифрование,
проверочный хеш ключа, дата создания, источники, версии и индекс `fileVersions`.
`cipher` обозначает используемый стандартный режим шифрования.

`containerPath` нужен текущей программе, но не записывается в JSON:
переносной контейнер может находиться на другом диске.
Для записи остальных полей используется внутренняя запись `Data`.
`fileVersions` содержит номера сохранённых изменений по каждому пути;
содержимое конкретного снимка определяется его `snapshot`.
`lastVersion` находит запись с наибольшим номером через `maxByOption`.

### Временные результаты

| Тип | Зачем он нужен |
|---|---|
| `WalkedFile` | Файл, который сейчас найден: путь, размер, время изменения и хеш |
| `LastRecord` | Файл из прошлого снимка и его источник |
| `ChangeReport` | Найденные изменения, проблемы, количества и объём данных |
| `ScanPlan` | Отчёт, ошибки и индексы успешно проверенных источников |
| `BackupResult` | Номер созданной версии, реальные счётчики и причины пропусков |
| `RestoreResult` | Сколько файлов восстановлено/пропущено и какие ошибки встретились |
| `VerifyResult` | Сколько блоков целые, какие повреждены и какие отсутствуют |

### JSON

JSON здесь разбирает готовая библиотека uPickle/uJson.
`derives ReadWriter` просит библиотеку создать код чтения и записи записи.
В `ModelJson` заданы только два правила представления наших данных:
`Option[String]` записывается как строка или JSON `null`, а переименование —
как объект с полями `from` и `to`.
Это сохраняет совместимость формата. Собственного разбора JSON-символов нет.

JSON `null` на диске не означает использование Scala `null` для ожидаемой
ошибки. После чтения нормальное отсутствие представлено значением `None`.

## 7. Конфигурация и журнал

В `backup.json` девять настроек:

| Настройка | На что влияет |
|---|---|
| `logFile` | Путь журнала |
| `keyDirectory` | Папка отдельных файлов ключей |
| `defaultContainerName` | Имя нового контейнера при Enter |
| `checkOnStorageOpen` | Автоматически проверять источники после открытия |
| `confirmBeforeBackup` | Спрашивать согласие перед записью копии |
| `confirmBeforeRestoreOverwrite` | Спрашивать перед заменой существующих файлов |
| `maximumVersionsPerFile` | Ограничивать старое содержимое каждого отдельного файла |
| `hashAlgorithm` | Вычислять отпечатки через SHA-256 или MD5 |
| `defaultExclusions` | Общие исключения для обхода источников |

`Config.load` читает текст, разбирает JSON и вызывает `validate`.
Проверяются обязательные строки, целое положительное число версий,
алгоритм, шаблоны, имя контейнера, возможность создать папку ключей и доступ к журналу.
Проверка типов JSON сделана явно: например, массив чисел не должен незаметно
стать массивом строк, а `null` не должен попасть в обязательное поле.

Команда reload заменяет настройки только после успешной загрузки и проверки.
Если новая конфигурация ошибочна, прежние настройки остаются в памяти.
Отсутствующий при перезагрузке файл также считается ошибкой.
При первом запуске стандартную конфигурацию отдельно создаёт `Main`.

`Logger` пишет время, уровень и событие с режимом `APPEND`.
Поэтому следующий запуск добавляет строки, сохраняя прошлый журнал.
`Logger` не печатает ошибку самостоятельно: возвращает `Left`, а интерфейс
решает, как её показать. Интерфейс не передаёт в журнал введённые ключи
и полные пользовательские команды.

## 8. Что делает каждая группа функций Menu

| Функции | Их роль |
|---|---|
| `event`, `logError`, `error`, `show` | Запись событий и безопасных категорий ошибок, показ результата и продолжение/отмена диалога |
| `read`, `path` | Чтение строки с учётом EOF и безопасное получение Path |
| `yes`, `readNumber` | Повторный вопрос при непонятном ответе |
| `withStorage` | Запрет операций, требующих ещё не открытое хранилище |
| `info`, `sources` | Показ текущих данных |
| `readSource`, `readSources` | Сбор одного или нескольких источников через Option |
| `changeSources`, `sourcesMenu` | Изменение списка по готовому SourceAction и подменю |
| `chooseDirectory` | Выбор доступной папки; при ошибке вопрос повторяется |
| `keyFile`, `newKey` | Безопасное имя файла ключа и выбор способа хранения |
| `create`, `open` | Подготовка аргументов и вызов соответствующей операции Container |
| `scan`, `backup`, `restore` | Показ отчётов и получение подтверждений перед операциями |
| `execute` | Выполнение выбранного варианта Command |
| `run` | Главный цикл интерфейса |

`show` не является частью бизнес-логики: он нужен именно интерфейсу.
Он превращает `Left` в показ сообщения и отмену текущей цепочки Option,
а успешное значение оставляет доступным в `Some`.

`var` у `cfg`, `opened`, `key` и `running` означает изменяемое состояние диалога.
ТЗ не требует полностью запретить `var` или внедрить State/IO.
Требование состоит в типизированных командах/ошибках и отделении интерфейса.

## 9. Как Scanner находит изменения

Алгоритм сканирования:

1. Взять включённые источники, не помеченные удалёнными.
2. Отдельно отметить недоступные источники.
3. Обойти доступные файлы и каталоги с учётом рекурсии и исключений.
4. Для каждого файла получить размер, время изменения и хеш.
5. Сравнить текущее состояние с последним `snapshot`.
6. Сформировать `ChangeReport` и `ScanPlan`.

У файла внутри первого источника путь может быть `s0/sub/a.txt`.
Это внутренний путь хранилища, а не абсолютный путь исходника.
`sourceIndexOf` получает из префикса номер источника, `resolveRel` определяет,
какой реальный файл нужно прочитать. Одиночный файл-источник обрабатывается отдельно.

Файл новый, если раньше для этого пути не было сохранённого содержимого.
Файл изменён, если его нынешний хеш отличается от прошлого.
Удаление фиксируется только при безопасно проверенном доступном источнике,
когда прежний путь отсутствует или стал каталогом. Это учитывает
и замену файла каталогом или каталога файлом. Неизвестный из-за ошибки доступа
статус пути сам по себе не означает удаление.

Если диск отключён или часть каталога не удалось прочитать, отсутствие файла
в результатах обхода не доказывает удаление. Поэтому программа сохраняет
предыдущее состояние вместо массового удаления таких записей.

Переименование определяется по совпадению размера и хеша среди новых и удалённых
файлов. Это вывод по содержимому: несколько одинаковых файлов невозможно
однозначно различить только по этим признакам.

`Glob` использует готовый механизм `PathMatcher` Java.
Шаблоны вроде `*.tmp` проверяются для относительного пути и его частей.
Символьные ссылки пропускаются. Каталог ключей, журнал, конфигурация
и сам контейнер исключаются из обычного сканирования интерфейса.

## 10. Что находится внутри .store

Контейнер — ZIP с другим расширением:

```text
demo.store
  meta/filerecords.json
  blobs/хеш_содержимого_первого_файла
  blobs/хеш_содержимого_второго_файла
```

В JSON лежат источники, версии и ссылки на содержимое.
В `blobs` — сами данные. Название блока связано с хешем содержимого,
поэтому одинаковые байты не требуют нескольких одинаковых записей ZIP.
Разные файлы и версии могут ссылаться на один блок.

Незашифрованный блок содержит исходные байты файла.
У зашифрованного блока эти байты защищены AES-GCM.
Метаданные, в том числе имена исходных путей, остаются открытыми.

Формат 2 — текущий формат. Незашифрованный формат 1 из ЛР0 читается с адаптацией
полей. Старый XOR-контейнер нужно восстановить через ЛР0 и сохранить заново.

## 11. Что происходит при резервировании

Интерфейс вызывает Scanner, показывает отчёт и получает согласие.
Затем `Container.backup` получает план и выполняет работу:

1. Проверить ключ, если хранилище зашифровано.
2. Собрать новые и изменённые файлы из отчёта.
3. Для каждого определить реальный путь и запретить копирование служебных файлов.
4. Прочитать свойства до копирования, байты файла и свойства после копирования.
5. Вычислить хеш прочитанных байт и сравнить с планом.
6. Отделить успешно прочитанные файлы от ошибок.
7. Повторно проверить доступность источников удалённых файлов и добавить отметки `FileRef(None, 0)` только для подтверждённых удалений.
8. Получить новый `snapshot`, сохранив прежние записи для пропущенных файлов.
9. Создать `VersionInfo`, применить лимит истории каждого файла и записать ZIP.
10. Вернуть обновлённые метаданные и реальные счётчики операции.

Дата последней успешной копии обновляется для каждого источника отдельно.
Для этого план хранит индексы источников без ошибок сканирования,
а копирование дополнительно учитывает неудачные чтения и удаления по источникам.
Ошибка одного источника не мешает обновить дату другого, успешно сохранённого.

Время изменения, размер и хеш сравниваются с планом. Если пользователь изменил
файл, пока отвечал на подтверждение, он уже отличается от показанного состояния.
Тогда получается `FileChanged`, и файл пропускается.
Именно поэтому в ручном тесте нужно дождаться «добавлено 1», прежде чем менять файл.

Ошибка одного файла не отменяет все остальные. Поэтому внутри обработки есть
список `Either`: у каждого файла свой результат. Успехи собираются в `saved`,
ошибки — в `problems`. При наличии проблем версия помечается `partial`.
Она может оказаться пустой, если не удалось сохранить ни одного файла.

`writeZip` переносит ещё нужные старые блоки, добавляет новые и записывает JSON.
Сначала создаётся временный файл рядом с целевым. Старый контейнер заменяется
только после успешной записи и закрытия ZIP. `replaceFile` также применяется
при восстановлении отдельных файлов.

`Using.resource` автоматически закрывает открытые потоки и архивы,
в том числе при исключениях. `finally` у временного файла удаляет его остаток.
Если атомарная замена не поддерживается файловой системой, `move` использует
обычную замену через стандартный Java API.

## 12. Как работает лимит версий

Лимит относится к содержимому каждого отдельного файла, а не к общему числу
снимков хранилища. `retain` оставляет последние разрешённые различные хеши
для каждого пути и удаляет из старых снимков ссылки на более старые данные.

Например, при лимите 2 и последовательности содержимого A → B → C
последнее содержимое C и предыдущее B остаются, а A может быть очищено.
Если другой файл ни разу не менялся, его единственное содержимое сохраняется.
Несколько снимков могут ссылаться на один и тот же оставшийся блок.

Урезанный старый снимок получает пояснение в `result`.
Его уже нельзя восстановить полностью: часть данных удалена по настройке.
Это видно в списке версий и перед восстановлением. Последнее сохранённое
содержимое каждого пути защищено от удаления самим лимитом.

## 13. Как устроены ключ и шифрование

`Crypto.generateKey` получает 32 случайных байта через `SecureRandom`
и представляет их текстом Base64. Это ключ, который показывается пользователю
или записывается в отдельный файл.

В метаданные записывается `keyCheck`: SHA-256 от ключа и названия хранилища.
При открытии программа вычисляет его заново и сравнивает.
Сам ключ в JSON хранилища не записывается.

Для AES функция `aesKey` получает байты ключа через SHA-256 его текстового вида.
Шифрование выполняет готовый `Cipher` из Java в режиме `AES/GCM/NoPadding`.
Случайный nonce длиной 12 байт добавляется к началу зашифрованного блока.
GCM также формирует тег проверки, позволяющий обнаружить изменение данных.
При расшифровке nonce читается из начала блока, а библиотека проверяет тег.

В режиме сохранения ключа `CREATE_NEW` защищает уже существующий файл ключа
от случайной перезаписи. В режиме показа требуется подтверждение пользователя.
После этого приложение хранит ключ в памяти текущего запуска.
В журнал передаются события и категории ошибок, а не введённый ключ.

Хеширование и шифрование имеют разные цели. Хеш помогает сравнить содержимое,
найти повторный блок и проверить целостность. Шифрование защищает содержимое
от чтения без ключа. Программа не реализует собственный криптоалгоритм.

## 14. Как работают восстановление и проверка целостности

`restoreConflicts` проверяет пути выбранного снимка и находит существующие файлы.
Интерфейс спрашивает разрешения и передаёт в `restore` набор разрешённых замен.
Нажатие «нет» означает нормальный пропуск, а не ошибку.

`restore` перебирает файлы выбранного `snapshot`. Записи с `hash=None`
не создают файл. Для остальных программа получает блок из ZIP, расшифровывает
при необходимости и проверяет хеш. Только потом пишет временный файл
и заменяет целевой. Поэтому повреждённый блок не должен затереть существующий файл.

`safeTarget` проверяет, что путь остаётся внутри каталога восстановления
и не проходит через обнаруженные символьные ссылки. Путь из метаданных нельзя
слепо дописывать к папке: иначе повреждённый контейнер мог бы указать `../...`.

Файлы источников попадают в подпапки `s0`, `s1` и так далее.
Это предотвращает столкновение одинаковых имён у разных источников.
Восстановление пишет файлы снимка, но не удаляет посторонние файлы из папки
назначения. Для проверки полного состояния удобно выбирать новую пустую папку.

`verify` проверяет все блоки, на которые ссылаются оставшиеся снимки.
Отсутствующий блок попадает в `missing`, ошибка расшифровки или хеша —
в `damaged`, успешно проверенный — в счётчик `ok`.
Алгоритм проверки конкретного блока определяется по длине сохранённого хеша:
32 шестнадцатеричных символа для MD5, 64 — для SHA-256.
Поэтому смена настройки алгоритма не мешает читать старые данные.
Поэтому `restore` и `verify` не принимают текущий алгоритм из конфигурации:
проверка существующего блока использует его собственный сохранённый хеш.

## 15. Зачем нужны автоматические проверки

`BackupChecks.scala` содержит 24 группы проверок.
Он создаёт отдельную временную папку, готовит маленькие файлы,
вызывает реальные функции проекта и проверяет результат через `assert`.

Проверяются конфигурация и неверные JSON-типы, журнал, разбор команд,
создание и открытие контейнера, рекурсия и исключения, дедупликация,
старый формат, защита ключей, изменения и переименования,
восстановление выбранной версии и конфликты, отключённые источники,
изменение файла после сканирования, лимит истории, одиночный источник,
смена алгоритма, верный/неверный ключ и повреждение зашифрованных данных.
Дополнительно проверяются исчезновение конфигурации, замена файла каталогом
и обратно, замена самого каталога источника файлом, отключение источника
между проверкой и копированием, независимые даты источников и небезопасные пути снимка.

`value` в тестах получает ожидаемый `Right`. Если пришёл `Left`, тест падает
с пояснением: в конкретной проверке предполагался успех. Это проверочный код,
поэтому `AssertionError` там нормален. Бизнес-операции вместо такого падения
возвращают типизированные ошибки.

`rewriteBlob` специально портит сохранённые байты, чтобы проверить обнаружение
повреждений и сохранность ранее существовавшего восстановленного файла.
Реальные пользовательские контейнеры автоматические проверки не изменяют.

## 16. Как проект выполняет требования ЛР1

| Требование | Где оно выполнено |
|---|---|
| Команды представлены ADT | `Command`, `SourceAction`, однократный `Command.parse` |
| Разные ожидаемые ошибки различаются | Варианты `AppError` с данными причины |
| Ожидаемые ошибки возвращаются значениями | `Either[AppError, ...]` у основных операций |
| Нормальное отсутствие явно | `Option` для ключа, открытого хранилища, комментария и других значений |
| Логика отделена от интерфейса | Вопросы и печать в `Menu`; операции в `Scanner`, `Container`, `Config`, `Crypto` |
| Преобразования контейнеров | `map`, `flatMap`, `filter`, `collect`, `foldLeft`, `for` |
| Функциональность ЛР0 сохранена | Источники, контейнеры, версии, шифрование, восстановление, настройки и журнал |

Не вся программа является чистой функцией. Чтение диска, запись ZIP и журнала
по определению взаимодействуют с внешним миром. Это допустимо.
Главное — не смешивать с ними консольные диалоги и не скрывать ожидаемые
ошибки за `null`, условным номером или исключением для обычного ветвления.

## 18. Запуск и короткая ручная проверка

Из папки проекта:

```powershell
scala-cli run . --server=false --main-class backup.backupApp
```

Автоматические проверки:

```powershell
scala-cli run . --server=false --main-class backup.backupChecks
```

Для ручной проверки создай источник с `a.txt`, сохрани в нём текст `Привет`,
создай контейнер и выполни пункт 6. После сообщения «добавлено 1»
измени исходный файл. Пункт 5 должен обнаружить изменение.
Затем пунктом 8 восстанови успешно сохранённую версию в новую папку.
В её подпапке `s0` должен оказаться файл с первоначальным текстом.
