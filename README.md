# Лабораторная работа №1. Переносное резервное хранилище

Консольное приложение для создания резервных копий файлов и каталогов,
ведения истории версий, восстановления данных и проверки целостности хранилища.

Цель лабораторной работы — рефакторинг исходного решения с применением
алгебраических типов данных и операций над функциональными контейнерами
при сохранении основных пользовательских сценариев.

Требования приведены в [Task1.txt](Task1.txt) и [Task3.md](Task3.md).
В качестве основы использовано решение ЛР0 из репозитория `filipp880/Lab_FP`,
коммит `c348211`.

## Технологический стек

- Scala 3.7.4.
- Java 17.
- uPickle/uJson 4.1.0 — сериализация и обработка JSON.
- Scala CLI и sbt — средства сборки и запуска.
- Java NIO, ZIP API и Java Cryptography Architecture — файловые операции,
  контейнерное хранение, хеширование и шифрование.

## Архитектура

Исходный код размещён в пакете `backup` каталога `src/backup`.

| Компонент | Назначение |
|---|---|
| `Main.scala` | Инициализация конфигурации и запуск приложения |
| `Menu.scala` | Консольный интерфейс, подтверждения операций и состояние сеанса |
| `Command.scala` | ADT команд `Command`, действий `SourceAction` и разбор ввода |
| `AppError.scala` | ADT ошибок `AppError` и преобразование исключений внешних API |
| `Models.scala` | Модели метаданных, снимков, изменений и результатов копирования |
| `Sources.scala` | Параметры источников и их валидация |
| `Config.scala` | Загрузка, проверка и сохранение конфигурации |
| `Glob.scala` | Проверка и применение правил исключения |
| `Scanner.scala` | Обход источников и сопоставление с последним снимком |
| `Container.scala` | Операции с контейнером, управление версиями и восстановление |
| `Crypto.scala` | Хеширование, генерация ключей и AES-GCM |
| `Logger.scala` | Регистрация событий в файловом журнале |

Пользовательский ввод преобразуется в `Command`; последующая диспетчеризация
выполняется по вариантам ADT. Ожидаемые ошибки представлены типом `AppError`
и передаются через `Either[AppError, A]`. Необязательные значения представлены
типом `Option`: открытое хранилище, ключ, комментарий, выбранная версия и дата
последнего успешного резервного копирования источника.

Консольное взаимодействие сосредоточено в `Menu`. Основные операции возвращают
данные и типизированные ошибки. Последовательная обработка результатов
и коллекций выражена через `map`, `flatMap`, `filter`, `collect`
и for-comprehension. Файловые ресурсы закрываются посредством `Using.resource`
или блоков `finally`.

## Сборка и запуск

Запуск из корневого каталога проекта через Scala CLI:

```powershell
scala-cli run . --server=false --main-class backup.backupApp
```

В Windows доступен сценарий `run.cmd`, устанавливающий кодировку UTF-8
и рабочий каталог проекта. При первом запуске Scala CLI загружает необходимые
компоненты JVM и зависимости, если они отсутствуют в локальном кеше.

Альтернативный запуск через sbt при наличии Java 17 или более поздней версии:

```powershell
sbt run
```

При отсутствии конфигурационного файла создаётся `backup.json` со стандартными
настройками. Относительные пути конфигурации разрешаются относительно текущего
рабочего каталога. Журнал `backup.log` и каталог ключей создаются в соответствии
с настройками.

## Командный интерфейс

Операции доступны через нумерованное меню и текстовые команды.

| Команда | Операция |
|---|---|
| `create` | Создание хранилища и первоначальная настройка источников |
| `open` | Открытие существующего контейнера |
| `info` | Вывод сведений о текущем хранилище |
| `sources` | Управление источниками через подменю |
| `scan` | Анализ изменений относительно последнего снимка |
| `backup [комментарий]` | Сохранение изменений с необязательным комментарием |
| `versions` | Просмотр сохранённых версий |
| `restore [номер]` | Восстановление выбранной версии; без аргумента — выбор в диалоге |
| `verify` | Проверка целостности сохранённых блоков |
| `reload` | Повторная загрузка и валидация конфигурации |
| `help` | Вывод перечня команд |
| `exit` | Завершение приложения |

Доступны также команды `sources list`, `sources add`, `sources edit <номер>`,
`sources remove <номер>`, `sources enable <номер>` и `sources disable <номер>`.
Пути, параметры источников, ключи и каталог восстановления вводятся в диалогах.

Существующий контейнер при создании не перезаписывается. Для открытия
зашифрованного хранилища требуется ключ; пустой ответ инициирует чтение
соответствующего файла `.key` из настроенного каталога.

## Конфигурация

Настройки хранятся в отдельном JSON-файле.

| Параметр | Назначение |
|---|---|
| `logFile` | Путь к журналу событий |
| `keyDirectory` | Каталог сохраняемых ключей |
| `defaultContainerName` | Имя контейнера по умолчанию |
| `checkOnStorageOpen` | Автоматический анализ изменений после открытия |
| `confirmBeforeBackup` | Подтверждение записи изменений |
| `confirmBeforeRestoreOverwrite` | Подтверждение перезаписи при восстановлении |
| `maximumVersionsPerFile` | Ограничение истории содержимого отдельного файла |
| `hashAlgorithm` | Алгоритм хеширования: SHA-256 или MD5 |
| `defaultExclusions` | Общие правила исключения файлов и каталогов |

Валидация охватывает формат и типы полей JSON, обязательные пути,
положительный лимит версий, поддерживаемый алгоритм хеширования,
корректность glob-шаблонов и доступность служебных путей.
Неудачная перезагрузка конфигурации сохраняет действующие настройки.

## Организация хранения

Контейнер представляет собой ZIP-файл с расширением `.store`.
Метаданные размещаются в записи `meta/filerecords.json`, содержимое файлов —
в записях `blobs/<хеш>`. Совпадающее содержимое использует общий блок данных.
Каждая версия включает снимок состояния, перечень изменений, время создания,
результат операции и необязательный комментарий.

Удаление исходного файла фиксируется в снимке отдельной записью.
Недоступные и отключённые источники исключаются из определения удалений.
Переименования определяются эвристически по совпадению размера и хеша.
Изменение файла между сканированием и чтением при резервном копировании
приводит к его пропуску с сохранением предыдущего состояния в снимке.

Лимит истории применяется отдельно к каждому файлу и сохраняет его последнее
содержимое. Частичное удаление данных старого снимка отражается в результате
соответствующей версии. Запись контейнера выполняется через временный файл
с последующей заменой целевого.

Файлы восстанавливаются в подкаталоги `s0`, `s1` и далее в соответствии
с постоянными индексами источников. Конфликты имён обрабатываются с учётом
настройки подтверждения перезаписи. Целостность блока проверяется до замены
существующего файла; посторонние файлы каталога назначения не удаляются.

## Шифрование и ограничения реализации

Для шифрования содержимого файлов используется AES-GCM. Поддерживаются
сохранение ключа в отдельном файле и передача ключа пользователю без сохранения.
Ключи и содержимое файлов исключены из журналирования. Каталог ключей,
конфигурация, журнал и текущий контейнер защищены от включения в резервную копию.

В текущем формате метаданные контейнера остаются незашифрованными.
Новые и изменённые файлы при резервном копировании загружаются в память целиком.
Поддерживается чтение незашифрованных контейнеров ЛР0. Контейнеры со старым
XOR-шифрованием требуют предварительного восстановления средствами ЛР0
и повторного сохранения в текущем формате.

## Тестирование

Интеграционные проверки реализованы в `tests/BackupChecks.scala`:

```powershell
scala-cli run . --server=false --main-class backup.backupChecks
```

Набор содержит 24 группы проверок: конфигурация и сериализация, разбор команд,
журналирование, создание и открытие контейнеров, обнаружение изменений,
дедупликация, история версий, восстановление, шифрование и обработка повреждений.
Дополнительно проверяются недоступность источников, изменение файлов после
сканирования, замена файла каталогом и обратно, независимый учёт успешности
источников и ограничения путей восстановления.

Тестовые данные размещаются в отдельном временном каталоге.
