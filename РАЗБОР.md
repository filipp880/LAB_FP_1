# Как объяснять программу на защите

Программа создаёт контейнер резервных копий, сравнивает исходные файлы с последним
снимком и восстанавливает сохранённое содержимое. Ниже — порядок чтения и смысл
операций. Библиотечные вызовы из последнего раздела нужно разобрать отдельно:
в присланных примерах они не объяснялись.

## Порядок чтения

| Файл | Что нужно понимать |
|---|---|
| `Main.scala` | Создание начальной конфигурации, загрузка, запуск меню |
| `Command.scala` | Превращение строки в один из вариантов команды |
| `AppError.scala` | Отдельный вариант для каждой причины ошибки |
| `Sources.scala`, `Models.scala` | Источник, ссылка на содержимое, версия, отчёты |
| `Menu.scala` | Ввод, подтверждения, вывод и состояние текущего сеанса |
| `Scanner.scala` | Обход источников и сравнение с последним снимком |
| `Container.scala` | Создание версии, лимит истории, восстановление, проверка |
| `ContainerFile.scala` | Физическое чтение и запись ZIP |
| `Crypto.scala` | Хеш, ключ доступа, вызовы готового AES-GCM |
| `Config.scala`, `Glob.scala`, `Logger.scala` | Настройки, исключения, журнал |

`Main` сначала сохраняет начальный `backup.json`, если файла ещё нет. Затем
загружает и проверяет конфигурацию. При успехе создаёт `Menu` и запускает `run`.
Цикл меню читает строку, `Command.parse` разбирает её, `execute` выполняет команду.
Открытое хранилище, ключ, настройки и флаг продолжения работы — поля `Menu`.

## defaultPath, create и отметка неудачного источника

В `Config` путь записан так:

```scala
val defaultPath: Path = Paths.get("backup.json")
```

`val` вычисляет и сохраняет значение один раз при инициализации объекта.
`def` описывает функцию: её тело выполняется при каждом вызове. Здесь путь
постоянный, поэтому достаточно `val`. `Path` — тип объекта, описывающего путь;
`Paths.get` создаёт этот объект из строки. Сам файл при этом не открывается
и не создаётся. Путь относительный: `backup.json` ищется в рабочем каталоге.
`toAbsolutePath` добавляет к относительному пути рабочий каталог. В `defaultPath`
это не нужно; вызов остаётся там, где сравниваются пути служебных файлов
или проверяется принадлежность пути каталогу восстановления.

В `Container.create` проверки идут последовательно. `return Left(...)` сразу
завершает функцию с ошибкой. Если включено шифрование, `key match` отдельно
рассматривает отсутствие ключа и имеющуюся строку. Пустая строка тоже отклоняется.
При непустом ключе вычисляется `Some(Crypto.keyCheck(value, name))`.
Без шифрования `keyCheck` остаётся `None`.

В `StorageMeta(name = name, containerPath = path, ...)` слева от `=` стоит имя
параметра класса, справа — передаваемое значение. Так видно назначение полей.
Списки версий и содержимое файлов сначала пусты. При первой записи шифровать
ещё нечего, поэтому в `ContainerFile.write` передаётся `key = None`;
`replacing = false` означает создание нового контейнера без замены существующего.

```scala
val writeResult = ContainerFile.write(meta, fileContents, key = None, replacing = false)
writeResult.map(result => meta)
```

Тип `writeResult` — `Either[AppError, Unit]`. `Unit` означает, что у успешной
записи нет отдельного результата; его единственное значение записывается `()`.
`map` превращает `Right(())` в `Right(meta)`, а `Left(error)` оставляет прежним.
Параметр `result` имеет тип `Unit` и не используется: после успешной записи
нужно вернуть уже созданные метаданные. Функция после `=>` вызывается при `Right`.

Логические знаки читаются так: `&&` — «и», `||` — «или», `!` — «не».
Например, `enabled && !removed` истинно, только когда источник включён
и не удалён. `sizeChanged || timeChanged` истинно, если изменился размер,
время или оба сразу. У `&&` правая часть проверяется только при истинной левой,
у `||` — только при ложной: когда ответ уже известен, лишняя проверка не нужна.

В `backup` функция `markFailedSource(rel)` запоминает номер источника,
у которого не удалось скопировать файл или подтвердить удаление. Это нужно,
чтобы не обновить ему дату последней успешной копии. `sourceIndexOf("s0/a.txt")`
возвращает `Some(0)`; при неподходящем пути получается `None`. Обычный `match`
добавляет найденный индекс в `failedSources`, а при `None` ничего не делает.
`failedSources` — изменяемый `ArrayBuffer[Int]`. Запись `failedSources += index`
добавляет в него число: буфер меняется на месте. `val` не позволяет заменить
сам буфер другим объектом, но позволяет изменять его содержимое.
Таким же образом накапливаются найденные файлы, ошибки и пути изменений.
`buffer.toList` получает обычный список для поля модели. Для числовой переменной
`bytes += file.size` означает прибавление: `bytes = bytes + file.size`.
Повторяющиеся номера допустимы: дальше важно только `contains(index)` —
встречалась ли ошибка у этого источника хотя бы один раз.

## ADT, Option и Either

ADT задаёт известный набор вариантов. Например, `restore 2` превращается
в `Command.Restore(Some(2))`. Затем `match` работает с командой. `WrongKey`,
`FileMissing(path)` и `VersionNotFound(number)` — разные варианты ошибок.
`message` содержит подготовленный текст для человека.

В шаблоне `"restore" :: number :: Nil` список состоит ровно из двух строк.
`Nil` — пустой список; `::` отделяет первый элемент от остальных.
`case (old, current)` даёт имена элементам пары, `_` означает неиспользуемое значение.

`Option[A]` имеет два варианта: `Some(value)` и `None`. Здесь отсутствие нормально:

- `opened = None` — хранилище ещё не открыто;
- `key = None` — для незашифрованного контейнера ключ не нужен;
- `comment = None` — пользователь не ввёл комментарий;
- `lastVersion = None` — ещё не было резервного копирования;
- `FileRef(None, 0)` — в снимке записано удаление файла.

`Either[AppError, A]` — результат операции: `Right(value)` или `Left(error)`.
Ошибка возвращается вызывающему коду; её показ и продолжение диалога относятся
к меню. Чтение файлов, JSON и криптографические вызовы могут бросать исключения
Java. На этой границе `catch` превращает их в понятный вариант ошибки.
`NonFatal` перехватывает обычные исключения, не все критические сбои JVM.

`map` меняет значение внутри контейнера. Например:

```scala
val timestamp = meta.lastVersion.map(version => version.timestamp)
```

Было `Option[VersionInfo]`, стало `Option[String]`. При `None` функция не вызывается.
В списке `files.map(file => file.rel)` каждый файл превращается в строку пути.

`flatMap` нужен, если следующий шаг уже возвращает контейнер. Например,
`file.flatMap(record => record.hash)` превращает `Option[FileRef]` в `Option[String]`.
Обычный `map` здесь дал бы `Option[Option[String]]`. Для `Either` следующая операция
выполняется только после `Right`; полученный `Left` передаётся дальше.
Для списка `results.flatMap(result => result.files)` объединяет списки файлов
источников в один список.

`getOrElse` выбирает значение при отсутствии, например текст «нет» для экрана.
`filter` оставляет подходящие элементы, `find` возвращает первое совпадение как
`Option`, `contains` проверяет наличие. `Map.get(path)` возвращает `Option[FileRef]`,
поскольку пути может не быть. `Map.updated(path, ref)` создаёт отображение с новой
записью; присваивание в `var snapshot` запоминает этот результат.

`list.lift(index)` — безопасный доступ по индексу: возвращает `Some(element)`
или `None`, если индекс вне списка. Например, `List("A", "B").lift(1)` даёт
`Some("B")`, а `lift(2)` — `None`. Этот метод отдельно изучается по коду:
в присланных материалах он не объяснён.

## Источники, снимки и изменения

`Source` хранит путь, рекурсивность, исключения, включение и дату успешной копии.
Удалённый из списка источник помечается `removed`, а его индекс сохраняется:
старые пути `s0/a.txt` должны по-прежнему обозначать тот же источник.

Снимок — `Map[String, FileRef]`. Ключ — внутренний путь, значение — хеш содержимого
и размер. Само содержимое лежит отдельно в `blobs/<хеш>`.
Например, запись для `s0/a.txt` со значением `FileRef(Some("abc..."), 3)` означает,
что файл первого источника имеет три байта и находится в блоке `blobs/abc...`.
Если у двух файлов одинаковый хеш, используется один блок.

При сканировании программа обходит включённые доступные источники, применяет
исключения и запоминает размер, время изменения и хеш каждого файла. Размер и время
проверяются до и после чтения. Служебные файлы и каталог ключей пропускаются.
Символьные ссылки не обходятся, чтобы не уйти по перенаправлению и не зациклиться.

Текущее состояние сравнивается с последним снимком:

1. Пути раньше не было — новый файл.
2. Путь был, хеш изменился — изменённый файл.
3. Прежнего файла больше нет, источник успешно проверен — удалённый файл.
4. У удалённого и нового совпали хеш и размер — возможное переименование.

Совпадение содержимого позволяет предположить переименование, но не доказывает
действие пользователя. При одинаковых копиях выбирается первое подходящее
соответствие. Недоступность источника или ошибка чтения не означает удаление.

`backup` повторно читает новые и изменённые файлы. Если размер, время или хеш
отличаются от плана сканирования, файл пропускается с `FileChanged`. Удаления
тоже проверяются повторно: отключение устройства после `scan` не должно удалить
прежние копии из нового снимка.

Новая версия начинается со старого снимка. Успешно прочитанные файлы заменяют
свои записи. В той же ветви `Right(content)` байты добавляются в `blobs`, размер —
в общий счётчик, а путь — в `added` или `modified`. Отдельный список успешно
прочитанных файлов для последующего разбора не нужен. Подтверждённые удаления
получают `FileRef(None, 0)`. При ошибке чтения снимок и счётчики не изменяются,
поэтому предыдущая копия остаётся доступной. Версия хранит номер, время,
необязательный комментарий, результат и списки изменений. Дата `lastBackup`
обновляется отдельно для успешно обработанных источников.

Лимит истории применяется к разным хешам каждого пути. При лимите 2 и истории
`A, A, B, C` остаются `B` и `C`. Старые ссылки на `A` удаляются, снимки с утраченными
данными помечаются частичными. У неизменившегося файла один хеш может оставаться
во многих снимках. Последнее содержимое файла сохраняется.
История хранится в `versions` и снимках этих версий. Отдельного списка номеров
версий для каждого файла нет: лимит применяется к хешам в самих снимках.

## Запись и восстановление

В `meta/filerecords.json` лежат источники и версии. Фактический путь контейнера
туда не записывается: ZIP можно перенести в другую папку.
Поддерживается только `format = 2`. Поле `cipher` контейнера и поле `removed`
каждого источника обязательны. Если их нет, чтение вернёт ошибку формата.
Старый `format = 1` отклоняется.
Лишнее поле `fileVersions` в прежних контейнерах формата 2 не используется
и при следующем сохранении больше не записывается.
`ContainerFile` собирает различные хеши, нужные сохранённой истории, в `wanted`.
Новые блоки подготавливаются отдельно. `copyOldBlocks` проходит по `wanted`,
для каждого старого блока получает запись по имени `blobs/<хеш>` через `getEntry`
и копирует её поток в новый ZIP. Если этот хеш уже есть среди новых блоков,
старая запись пропускается. Затем записываются новые блоки и JSON.
Каждый хеш встречается в `wanted` один раз, поэтому повторная запись не нужна.

`getEntry` — API Java, возвращающее `null`, если имени в ZIP нет.
`Option(zip.getEntry(name))` сразу превращает его в `None`, а найденную запись —
в `Some(entry)`. Это преобразование требуется на границе с Java.

Новый ZIP сначала пишется во временный файл рядом с контейнером. После успешного
закрытия архива `Files.move` заменяет целевой файл. `finally` закрывает ресурсы
и удаляет оставшийся временный файл при успехе и при исключении.
Обычный `move` не обещает атомарную замену при отключении питания.

Восстановление выбирает снимок, пропускает маркеры удаления и для каждой записи:

1. Строит путь внутри выбранного каталога и проверяет, что он не выходит наружу.
2. Проверяет отсутствие символьных ссылок в пути и его родительских каталогах.
3. Учитывает решение о перезаписи существующего файла.
4. Читает блок, расшифровывает при необходимости и сверяет хеш.
5. Создаёт нужные папки, пишет временный файл и переносит его на место.

За чтение содержимого отвечает `plainBlob`. `storedResult` — результат чтения
блока, `decodedResult` — его расшифровки, `checkedResult` — проверки хеша.
Все три значения имеют тип `Either[AppError, Array[Byte]]`. Следующая стадия
через `flatMap` выполняется только после успеха предыдущей. При ошибке чтения
расшифровка не запускается; при ошибке расшифровки хеш не проверяется.
Незашифрованные байты передаются в проверку без изменения.

`normalize` сворачивает `.` и `..`, `Path.startsWith` сравнивает компоненты пути.
Одного сравнения мало: ссылка внутри каталога может вести наружу. Поэтому
проверяется цепочка родителей. Повреждённый блок не заменяет существующий файл.
Посторонние файлы в каталоге назначения программа не удаляет.

`verify` проходит по различным хешам сохранённых снимков. Отсутствующая ZIP-запись
попадает в `missing`, ошибка расшифровки или несовпадение хеша — в `damaged`.
Это проверка данных контейнера, она не сравнивает их с текущими исходными файлами.

## Настройки, JSON и журнал

`Config.validate` проверяет значения и свойства путей без записи и создания папок.
Права могут измениться после проверки, поэтому ошибки записи обрабатываются
в самой операции. Каталоги ключей и восстановления создаются там, где они нужны.
Журнал родительские каталоги не создаёт. При неудачном `reload` старый конфиг
остаётся действующим.

uJson хранит JSON как дерево значений. `ujson.read(text)` разбирает текст,
`ujson.write(json, indent = 2)` получает текст. `Obj()` создаёт объект,
`json("name") = value` записывает поле. `.str`, `.bool`, `.num`, `.arr`, `.obj`
читают строку, логическое значение, число, массив и объект. Несовпадение типа
перехватывается как ошибка формата. `Some(text)` сохраняется строкой, `None` —
JSON-значением `null`; внутри программы используется `Option`.

`Logger` дописывает время и событие через `APPEND`, а не очищает файл.
В журнал передаются подготовленные сообщения. Ключи, содержимое файлов и полный
пользовательский ввод туда передавать нельзя.

## Что в Crypto нужно изучить отдельно

Хеш нужен для сравнения и проверки содержимого, шифрование — для ограничения
доступа к нему. `MessageDigest.getInstance(name)` выбирает алгоритм,
`digest(bytes)` вычисляет хеш. Поддерживаются SHA-256 и MD5. Первый даёт 64
шестнадцатеричных символа, второй — 32; по длине сохранённого хеша выбирается
алгоритм проверки старого блока.

`hex` преобразует байты хеша в строку. Scala `Byte` имеет диапазон −128…127.
При отрицательном значении прибавляется 256: получается число 0…255.
`Integer.toHexString` переводит его в шестнадцатеричный вид. Однозначному
результату добавляется ноль: 5 становится `05`, −1 становится `ff`.
`map` преобразует каждый байт, `mkString` соединяет строки.

`SecureRandom` заполняет 32 байта случайными значениями; Base64 превращает их
в печатаемый ключ. Base64 — кодировка. `keyCheck` хранит SHA-256 от строки
`ключ:название`, чтобы проверить введённый ключ без сохранения самого ключа.
`aesKey` получает 32 байта SHA-256 от текстовой строки ключа и создаёт
`SecretKeySpec` для AES. Этот способ рассчитан на генерируемый случайный ключ.

`Cipher.getInstance("AES/GCM/NoPadding")` выбирает готовое шифрование Java.
`init` задаёт режим, ключ и параметры, `doFinal` выполняет операцию.
`GCMParameterSpec(128, nonce)` задаёт проверочный тег длиной 128 бит, то есть
16 байт. Случайный `nonce` занимает 12 байт и сохраняется перед шифротекстом.
Блок устроен так: `12 байт nonce | шифротекст | 16 байт тега`.
Поэтому менее 28 байт — уже повреждённый блок. При расшифровке `take(12)`
берёт nonce, `drop(12)` — остальную часть. Java проверяет тег; при повреждении
операция возвращает ошибку приложения.

JSON-метаданные, имена файлов и хеши остаются открытыми. Файлы при сканировании,
копировании и восстановлении читаются в память целиком. Чтение целиком заменяет
буфер и цикл потокового хеширования, но требует больше памяти; очень большой файл
может её исчерпать. Эти особенности решения следует уметь объяснить вместе
с самим алгоритмом.

## Остальные непройденные API

| Вызовы | Назначение |
|---|---|
| `Files.createDirectories` | Создать нужную папку с отсутствующими родителями при записи |
| `Files.readAllBytes`, `Files.size`, `getLastModifiedTime` | Прочитать байты и проверить свойства файла |
| `newDirectoryStream`, `FileSystems.getRootDirectories` | Получить содержимое папки и корни дисков |
| `isSymbolicLink`, `Path.resolve`, `normalize`, `startsWith` | Проверить и построить файловые пути |

| `ZipFile`, `ZipEntry`, `ZipOutputStream` | Читать ZIP-записи и создавать архив |

Часть обычных `Files`/`Paths` и `try/catch` есть в `01_UserCli.scala`, но это
не означает, что ZIP, GCM, JSON и все перечисленные методы уже пройдены.
Для подготовки полезно на одном маленьком файле проследить путь от `scan`
к `backup`, найти его запись в снимке и объяснить, что изменится при удалении,
ошибке чтения и восстановлении старой версии.
